## Решение пользователя и неизменяемые границы

- srv2: Git-репозиторий `/data/atlas`, недельный сбор, браузерные проверки и вызов
  прежней модели `openai/gpt-6.1-sol` через профиль Projectmanager.
- Local Ru (`194.87.143.141`): рабочая база, сайт, кабинет и теперь также
  постоянные кэш модели, журналы, диагностические файлы и дампы.
- Расписание сбора прежнее: понедельник 06:00 UTC (09:00 МСК).
- Порядок: туннель → удалённый дамп → недельный сбор → предпросмотр → axe-core →
  публикация → итог/оповещение. Правила классификации, промпты, модель и номера
  материалов не менялись. Общий кэш текстов Radar не переносился и не очищается.
- Эталон октября, prototype и тестовые данные в Git остаются частью исходников.

## Что и где изменено

- `atlas/storage.py`: клиент ограниченного SSH JSON RPC. Конфигурация srv2
  `/etc/atlas-storage/client.json`, отдельный ключ `/root/.ssh/atlas_storage`.
  Не выводить содержимое закрытых настроек и ключей в отчёты.
- `deploy/storage_server.py`: на Local Ru установлен как
  `/opt/atlas-storage/storage_server.py`. Forced command не предоставляет shell.
  Запись кэша, журналов и артефактов идёт в `/var/lib/atlas/storage/`;
  `pg_dump` выполняется на Local Ru и пишет в `/var/backups/atlas/`.
- `atlas/model.py`: стандартный кэш использует удалённое хранилище при наличии
  клиентской конфигурации. Runner выдаёт lease через `ATLAS_STORAGE_TOKEN`.
  Ручной вызов модели без lease не должен обходить защиту локальным кэшем.
- `atlas/weekly.py`, `scripts/weekly.sh`: новый runner, удалённые журналы,
  остановка группы дочерних процессов при таймауте/отказе хранения.
- `deploy/atlas-weekly.service`: установлен на srv2. RAM 768 MiB, swap 256 MiB,
  tmpfs 192 MiB, не более 12 часов. Root cron запускает службу, не второй runner.
- `deploy/storage_retention.py`: установлен в `/opt/atlas-storage/` Local Ru.
  `atlas-storage-maintenance.timer` ежедневно 04:30 UTC запускает дамп и очистку.
- `scripts/check_storage.py`: srv2, ежедневно 06:15 UTC, проверка обслуживания
  и оповещение об ошибке. `scripts/cleanup_local.py --apply`: 06:25 UTC,
  только старые dev-кэши Atlas; Git, venv и другие проекты исключены.
- `tests/test_storage.py`: проверки ограничений путей, кэша, блокировок,
  архивации, защиты бэкапов и завершения дочерних процессов.

## Что нельзя вернуть случайно

1. Не создавать заново `/data/atlas/var` как постоянный рабочий spool.
   При отказе Local Ru прогон останавливается, локального fallback нет.
2. Не возвращать `pg_dump` на srv2 через туннель. Дамп создаёт Local Ru.
3. Не удалять снимки версий в БД или общий кэш Radar в рамках retention Atlas.
   Lease активного прогона, `.pin`, последние два проверенных дампа защищены.
4. Не запускать старый cron параллельно `atlas-weekly.service`.
5. Не подменять модель/профиль, не переносить сбор на Local Ru без нового решения.
6. Не выкладывать старый шаблон Caddy поверх живой конфигурации:
   `/etc/caddy/atlas.agpm.space.caddy` содержит ранее подключённый счётчик Pult.
   Во время переноса хранения Caddy не менялся.
7. `scripts/deploy_code.sh` выкладывает приложение; установка storage-helper,
   maintenance и weekly units — отдельная операция. Не считать их автоматически
   обновлёнными после обычного deploy приложения.

## Проверки состояния без запуска сбора

На srv2:

```sh
git -C /data/atlas status --short
systemctl status atlas-weekly.service --no-pager
journalctl -u atlas-weekly.service -n 30 --no-pager
```

На Local Ru:

```sh
systemctl status atlas-storage-maintenance.timer --no-pager
systemctl status atlas-storage-maintenance.service --no-pager
journalctl -u atlas-storage-maintenance.service -n 30 --no-pager
systemctl status atlas-editor.service --no-pager
readlink /srv/atlas.agpm.space/current
```

Не путать проверки с запуском:

- `systemctl start atlas-weekly.service` на srv2 — настоящий сбор и возможная публикация.
- `atlas.weekly --check` — без сбора/публикации, **но создаёт дамп и журналы**.
- Retention без `--apply` — dry-run; обслуживание с `--backup --apply`
  создаёт дамп и может удалить допустимые политикой старые файлы.
- One-shot служба после успешного окончания может быть `inactive`: смотреть
  результат последнего запуска и журнал, а не только признак активности.
