# Инструкция дежурного, v1

1 ноября 2026 · что делать при каждой тревоге атласа, как откатить и перезапустить

## Где что

| | Где |
| --- | --- |
| Недельный прогон | управляющий сервер, `/data/atlas/scripts/weekly.sh`, crontab root, пн 09:00 МСК; журнал — `/data/atlas/var/weekly-<дата>.log` |
| База | Local Ru, PostgreSQL 17, база `atlas`; с управляющего сервера — только через туннель (`atlas-tunnel@`) |
| Сайт | Local Ru, `/srv/atlas.agpm.space/current` → `releases/<версия>/` |
| Кабинет | Local Ru, `atlas-editor.service`, 127.0.0.1:8790, снаружи `https://atlas.agpm.space/editor/` |
| Код на Local Ru | `/opt/atlas/current` → `releases/<коммит>`, окружение `/opt/atlas/venv` |
| Настройки | Local Ru `/etc/atlas/atlas.env`, пароль базы `/etc/atlas/db.pass`; управляющий сервер — `/root/.config/atlas/db.pass` |

Команды на Local Ru выполняются от пользователя `atlas` с настройками службы:

```
sudo -u atlas bash -c 'set -a; . /etc/atlas/atlas.env; set +a; cd /opt/atlas/current; /opt/atlas/venv/bin/python -m atlas.cli <команда>'
```

## Тревоги

**«До 18:00 выгрузка радара недоступна или выпуска нет».** Прогон повторял
запрос каждый час и сдался. Проверить `curl -s https://radar.agpm.space/api/health`. Когда радар
ожил, запустить прогон заново: `bash /data/atlas/scripts/weekly.sh <дата среза>`.
Если не запускать, следующий понедельник заберёт две недели.

**«Туннель к базе».** ssh не поднял туннель к Local Ru. Проверить
`ssh -i /root/.ssh/atlas_tunnel -N -L 55432:127.0.0.1:5432 atlas-tunnel@radar.agpm.space`
и что PostgreSQL на Local Ru работает (`systemctl status postgresql`).
Перезапустить прогон.

**«Прогон, код N».** Подробности в журнале прогона. Ответы модели
кэшируются, поэтому повторный запуск не тратит обращений на уже разобранное.
Если модель недоступна, материалы переходят в «перенесено» и разберутся в
следующий раз — это не тревога.

**«Проверка доступности нашла серьёзные нарушения».** Перед публикацией прогон собирает
предпросмотр `/v/<версия>/` и проверяет его axe-core. Отчёт — `/data/atlas/var/a11y-<версия>.json`.
Нарушения появляются после изменений кода сайта, а не данных. Исправить, выложить
код, пересобрать версию (`atlas.cli rebuild-site`), опубликовать из кабинета.

**«Версия не опубликована и ждёт кабинета».** Сработала блокирующая проверка
или предохранитель «резкие изменения». Причина — в тексте оповещения и в ленте
кабинета. На сайте остаётся прежняя версия. Решение за редактором: кнопка
«Опубликовать» или правка и новый выпуск.

## Откат

Из кабинета: «Лента изменений» → опубликованная версия → причина → «Откатить
сайт на эту версию». Без кабинета (например, если служба лежит):

```
sudo -u atlas bash -c '… python -m atlas.cli rollback --version 2026-10-27-2 --reason "<почему>" --actor <кто>'
```

Откат возвращает и сайт, и данные к снимку версии. Материалы, добавленные
после неё, исключаются с причиной «отменено откатом». Номера не
переиспользуются, и следующий прогон их не вернёт. Если не открывается и
командная строка, сайт возвращается одним переключением указателя:

```
cd /srv/atlas.agpm.space && ln -sfn releases/<версия> .current.new && mv -T .current.new current
```

Так меняется только сайт. Данные базы выровнять потом командой `rollback`.

## Перезапуск

- Кабинет: `systemctl restart atlas-editor`, журнал — `journalctl -u atlas-editor`.
- Внеочередной прогон: `bash /data/atlas/scripts/weekly.sh <дата среза>` на управляющем сервере.
- Выкладка кода: `bash /data/atlas/scripts/deploy_code.sh` на управляющем сервере из чистого дерева.

## Резервные копии

Недельный прогон перед забором сам снимает копию базы через туннель:
`/data/atlas/var/backups/atlas-before-week-<дата>.dump` на управляющем сервере.
Восстановление — в пустую базу (`DROP DATABASE … ; CREATE DATABASE atlas OWNER
atlas; pg_restore -d atlas <копия>`). Сообщение `transaction_timeout` при
восстановлении безвредно: так ведёт себя `pg_dump` 17.
Снимки версий хранятся в базе всегда, собранные папки сайта — 90 дней.
Папку старой версии можно пересобрать из снимка: `atlas.cli build-site --version <id>`.


## Выкладка кода сайта

После `bash /data/atlas/scripts/deploy_code.sh` папки версий на Local Ru пересобираются
под новый код, данные версий не меняются:

```
sudo -u atlas bash -c 'set -a; . /etc/atlas/atlas.env; set +a; cd /opt/atlas/current; for v in $(psql -Atc "select id from versions where state in ('"'"'current'"'"','"'"'published'"'"') order by slice, id" atlas); do /opt/atlas/venv/bin/python -m atlas.cli rebuild-site --version $v; done'
```

## Картинка для соцсетей

Одна на весь сайт: все страницы, включая архивные версии, ссылаются на
`https://atlas.agpm.space/og.png`. Источник — `site/assets/img/og.png` в
репозитории (PNG 1200×630, не больше 2 МБ; гейт это проверяет). Недельный
прогон картинку не трогает. Заменить: положить новый файл по тому же пути,
закоммитить, выложить код (`scripts/deploy_code.sh`) и пересобрать папки всех
версий командой выше. Telegram и другие сети помнят превью уже отправленных
ссылок и обновят его не сразу.
