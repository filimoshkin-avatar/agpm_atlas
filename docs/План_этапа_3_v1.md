## Как будет устроено

```
управляющий сервер (fra-1)                     Local Ru (msk-1, 194.87.143.141)
──────────────────────────                     ─────────────────────────────────
crontab root, пн 09:00 МСК                     PostgreSQL 17: база atlas, роль atlas

      пишет решения в базу                     /opt/atlas: код и окружение Python
  └ по ssh: «собрать и опубликовать» ────────► atlas publish: пересчёт, сборка, проверки,

                                               /srv/atlas.agpm.space/current → releases/…

                                               Caddy: atlas.agpm.space → current, /v/*, /editor/*
```

## Что меняется на Local Ru

Каждый пункт — изменение прода, делается только с согласия заказчика.

1. **PostgreSQL.** Новая база `atlas` и роль `atlas` с паролем. `pg_hba.conf`
   не меняется: вход по паролю с 127.0.0.1 уже разрешён. Базы KX, tea, nrd не
   затрагиваются.
2. **Перенос базы** с управляющего сервера: `pg_dump` → `pg_restore --no-owner
   --no-privileges`, несколько мегабайт. После переноса база на управляющем
   сервере переименовывается в `atlas_control_archive_20261101`. Тогда команда,
   по ошибке запущенная без туннеля, упадёт, а не запишет в старую копию.
3. **Системный пользователь `atlas`** и `/opt/atlas`: код и окружение Python
   (psycopg, jinja2, argon2). Код приезжает выкладкой с управляющего сервера,
   доступ Local Ru к GitHub не нужен.
4. **Пользователь туннеля `atlas-tunnel`** с ключом, которому разрешено только
   перенаправление на 127.0.0.1:5432, без оболочки.
5. **Папка сайта** `/srv/atlas.agpm.space/` с версиями и указателем `current`.
   Собранные папки хранятся 90 дней — это около 12 МБ на версию.
6. **Служба `atlas-editor.service`** — кабинет на 127.0.0.1, ограничение
   памяти 200 МБ.
7. **Блок `atlas.agpm.space` в Caddy** — отдельным файлом
   `/etc/caddy/atlas.agpm.space.caddy` и строкой `import` в Caddyfile, как
   у `tea.aipractice.space`. Подключается только после того, как DNS указывает
   на Local Ru, иначе Caddy зря будет просить сертификат:
   - корень — `current`, `/v/<дата>/` — из `releases`, `/editor/` — на кабинет;
   - ассеты с хэшем в имени отдаются immutable, страницы — no-store;
   - кабинет и снимки закрыты от индексации.
   Текст блока показываю до применения. Перед правкой — копия Caddyfile, после
   неё — `caddy validate`.

## Что меняется в другом месте

8. **DNS:** запись A `atlas.agpm.space → 194.87.143.141`. Её заводит заказчик у
   регистратора; HTTPS-сертификат Caddy получит сам.
9. **Расписание:** строка в crontab root на управляющем сервере,
   `0 6 * * 1 /data/atlas/scripts/weekly.sh` — понедельник, 09:00 МСК. Новый
   юнит systemd не нужен. Прогон ждёт выпуск радара за понедельник: если в
   09:00 его ещё нет, повтор каждый час до 18:00.
10. **Оповещения:** сводка после публикации и тревога при сбое уходят в
    Telegram через `openclaw message send`. Кому их слать — вопрос к заказчику.

## Что пишу в коде

- `atlas publish`: пересчёт, сборка папки версии, блокирующие проверки
  (целостность, номера, потери, цифры, правило сигнала 26 из 26, резкие
  изменения, сайт), атомарное переключение `current`, журнал;
- `atlas rollback <версия>` — откат за минуту, с причиной;
- `atlas week` — повторы каждый час до 18:00, если выгрузка недоступна, и
  тревога; без новых материалов версия не создаётся;
- **минимальный кабинет:** вход (argon2, защита от перебора, сеанс 12 часов),
  лента изменений, очередь, кнопка «Опубликовать» для задержанной версии,
  откат;
- `Инструкция_дежурного_v1.md`.

## Порядок

1. Код и конфиги готовы и проверены на управляющем сервере (сделано). Прод на
   этом шаге не менялся.
2. Заказчик заводит запись DNS и даёт согласие на пункты 1–7.
3. Применяю пункты 1–6 на Local Ru, выкладываю код, переношу базу, завожу
   учётную запись редактора. Сайт и кабинет проверяю на Local Ru через
   127.0.0.1.
4. Когда DNS указывает на Local Ru, подключаю блок Caddy: копия Caddyfile,
   `caddy validate`, перезагрузка.
5. Публикуется версия 2026-10-27-2, включаются расписание и оповещения.
   Первый плановый прогон, 03.11, заберёт неделю 28.10–03.11.

## Видимое следствие публикации

Публикация 2026-10-27-2 уводит в архив и три промежуточные версии: 2026-10-13,
2026-10-20 и 2026-10-27. Их снимки откроются по адресам `/v/…`. В снимке
2026-10-20 видны две смены сигнала, которые заказчик потом отменил. Это
прозрачно: в 2026-10-27-2 есть строка «Уточнения редакции». Другой вариант —
не показывать в архиве версии, которые никогда не были на сайте.

## Что не входит в этот шаг

Проверки доступности axe-core, хранение собранных папок 90 дней, оповещения
на почту, картинка для соцсетей, фильтр «только новые» — этап 4. Почте нужен
адрес от заказчика.

Проверка этапа: догрузка проверена редактором, затем 4 недельных прогона
подряд без вмешательства.
